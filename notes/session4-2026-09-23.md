# Session 4 (2026-09-23): GPS, vehicle data, browser

Goal: bring the car to life (position, gear, odometer, battery, map region) so the UI stops
treating it as "no car attached". Details and usage are in `vehicle/README.md`; this note is the
story and the loose ends.

## GPS (done, tested in the sandbox)
- `QtCarGpsManager` reads NMEA from UDP :63277 (any sender). It only publishes a fix after GGA +
  a complete GSV set + RMC in one epoch (found in `GPSThread::parse_nmea`: flags for GGA, RMC and
  "last GSV message" must all be set). With only RMC+GGA it never sets `LOC_geoValidFix`.
- QtCar draws the car at GpsManager's *estimate* whenever `LOC_estimatedGPSValid` is true. The
  estimator only follows GPS when the car reports speed, and it sets that flag to true on every
  start; it's only reset when `LOC_enableSmoothGPSUpdates` changes. That made the first tests look
  random. Fix: `GUI_smoothGPSUpdates=false` in QtCar's DB (start_all.sh) and `tesla-gps.py` keeps
  `LOC_estimatedGPSValid` false in GpsManager (:4160) and QtCar (:4220) over HTTP.
- `tesla-gps.py --to LAT,LON` routes with the firmware's `valhalla_client` on the host (clean
  env, `LC_ALL=C`) and drives along the shape with the route's speeds.

## Vehicle data (done, tested in the sandbox)
- Transport: CAN frames as UDP datagrams, 2-byte big-endian id + 8 bytes, broadcast to :1234,
  into `qtcar-vehicle`. Found by running `QtCarSimService` under strace.
- `QtCarSimService` (no args needed) = Tesla's simulated gateway: car config (0x7FF, map region
  USCanada), BMS (range 325 mi), HVAC, doors, ... about 40 ids. `SIM_*` values are readable and
  settable over HTTP :4190. No DI frames with the drive rail off; with `SIM_driveRailOn` it
  simulates the DI too, but gear/speed ignore `SIM_shiftState`/`SIM_vehicleSpeed` (speed raw 0 =
  −40 km/h). Kit group `vehicle` now makes `SimDriveInverter::send2Hz/send10Hz` return at once.
  Options it knows: `--no-gps`, `--no-carconfig`, `--van`.
- The signal database: `GUICanCracker::crackMessage` (libQtCarVAPI, 430 KB of generated code for
  the diag CAN viewer) decodes all 379 messages and calls `storeSignalValue(hash, value, valid)`.
  `vehicle/extract-can-db.py` runs it in Unicorn with bit-flip frames and gets every signal's
  layout (8759/8759, mux branches included). Hash → name/unit/enum from libQtCarCANData tables
  (`ETH_messages`, `ETH_<msg>_signals`, `Diag_<sig>_map`). Checksum algorithm from
  `VehicleUtils::calculateChecksum`.
- `tesla-can.py`: signals by name, presets, runtime `--set`, SIM_* passthrough, pauses ids the sim
  sends. Verified: odometer, gear, speed (`DI_uiSpeedHighSpeed` is the one QtCar uses), drive
  rail → speed display, map follows the drive, day/night, 72 °F, 325 mi.
- Car config from the sim gets persisted (VAPI_* in QtCarSettings.db) and QtCar/QtCarVehicle
  restart once ("DVs changed"). Once, QtCar then crashed at startup in `ProfileManager::instance`
  ("singleton recursively requested"): that was an assert, and asserts were fatal (see below,
  `utils-assert-nonfatal`), so it should only log now.

## Sandbox tooling (new)
- `./sandbox.sh`: QtCar + services in rootless podman, QtCar under the *host's* gdb (host `/`
  mounted at `/host`, gdb run with the host loader), `WebKitView::createBrowserClient` skipped via
  a breakpoint (CEF kills QtCar without escalator). Restart loops, screenshots.
- Touch without root: `tesla-touch --display :97` works as the user (ACL on /dev/uinput), the
  event node goes into podman with `--device`. `xdotool` clicks on :97 become touches.
- HTTP data values (`_data_get_value_request_`) are the best probe of what QtCar knows.
- `/tmp` inside `sandbox/rootfs` persists between runs (old logs pile up there).

## Crash fix after the first real run (logs/20260923-175710)
- QtCar segfaulted in `Logger::logAssert`: outside `RuntimeEnv` "prod" mode it writes to address
  0 after logging, on purpose. Trigger: qtcar-vehicle restarting after the first car config ->
  steering wheel button values go invalid -> QtCar sees a media button press -> "no currently
  playing controller" assert. New core patch `utils-assert-nonfatal` (jumps over the write).
  The GPSReaderThread/QtCar segfaults at `libQtCarUtils[b4703]` earlier in the kernel log were
  the same thing.

## GPS from a real receiver
- `tesla-gps.py --uart DEV --baud N` forwards NMEA line by line (termios, no pyserial);
  GpsManager knows GN/GL talker IDs. Tested with a pty emitting a u-blox-M8-like stream.

## Browser (works in the sandbox, 2026-09-23 evening)
- `./sandbox.sh --browser` runs CEF in the sandbox. Sandbox-only stub (`sandbox_escalator_stub.so`):
  `Escalator::runCommand()` -> 0, fake `/proc/self/cgroup` (`net_cls:/nonet`) for
  tesla-cef-launcher, and a SIGSEGV handler that prints backtraces of CEF child processes.
- Findings, all in the kit now (see mcu3-patchkit/README.md, Notes):
  - `cef_settings_t.no_sandbox` is at offset 8 in this CEF (3.3683); dumped QtCar's settings.
  - missing `v8_context_snapshot.bin` link next to the libcef symlink.
  - the "AVX crash" is WebAudio on a stub FFT: `createOscillator()` -> null.
  - EGL shim geometry bug.
- Result: tesla.com loads (DevTools on :9222 shows the title) and is drawn in QtCar's browser
  panel; parts of the page stay empty (Chrome 73).
- In the sandbox QtCar runs as root, and Chromium refuses to run as root without --no-sandbox;
  that exit was the first thing the no_sandbox fix got past.

## Real chroot (logs/20260923-200335 and later)
- `VEHICLE=1` + `GPS=...` drive and the browser work in the real chroot.
- First start crashed when the browser opened ("Memory corruption detected"): the escalator had
  exited after QtCar asked it to start the dashcam daemon, and `ChromiumManager::initializeCef`
  crashes without it. `startup.sh` now keeps the escalator in a respawn loop (marked by its
  `escalator-loop` command line) and waits for `/tmp/escalator`. Why the escalator exits is
  unknown (its binary is root-only).
- `/home/tesla-cef` (CEF cache, cookies) is now 0775: QtCar runs as tesla (group tesla-cef).
- Harmless: GPU process falls back to software (EGL fails, the firmware's swiftshader dir is empty).
