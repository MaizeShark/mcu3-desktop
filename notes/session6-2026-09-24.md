# Session 6 (2026-09-24): tools and user friendliness

Goal: no new features; make the existing tools easier to use. Usage is in `../README.md` (now a
user guide); this note covers the design and the loose ends.

## ./tesla (replaces start_all.sh)
- `./tesla start|stop|status|check|logs|config|services|build-image`. `start_all.sh` is a
  one-line alias for `./tesla start` (environment variables still work).
- Settings: `tesla.conf` (untracked; copied from `tesla.conf.example` at the first start, all
  lines commented = defaults). Order: defaults (`set_defaults` in `tools/common.sh`) < tesla.conf
  < environment < command line options. Relative paths from the environment/command line are
  relative to the caller's directory, from tesla.conf to the repo. `./tesla config` shows each
  value and its source; unknown names in tesla.conf are reported as typos by the checks.
- `--color/--wheels/--performance` imply `--vehicle`.
- Start: checks (`tools/check.sh`; only WARN/FAIL shown, FAIL stops unless `--force`),
  `sudo -v`, then the old start_all.sh steps. QtCar's output goes only to qtcar.log (`-v` shows
  it). A summary block at the end says what runs and where.
- Run state in the log folder: `state` (START_PID, CHROOT, MOUNTED_IMAGE, ports), `pids`
  ("pid starttime name" of the host helpers; the start time guards against reused pids),
  `events.log` (epoch, time, event: start, running: SERVICES, qtcar start/exit + restart reason,
  stop), `config` (effective settings). `logs/current` -> the running run, `logs/latest` -> the
  last one.
- A sudo keepalive (`sudo -n -v` every 60 s) runs during a start, so the cleanup after
  `./tesla stop` from another terminal (hours later) doesn't wait for a password in the first one.
- `./tesla stop`: SIGTERM to START_PID (its EXIT trap does the teardown), waits up to 30 s. Then
  looks for leftovers without sudo (firmware process names via pgrep, helper pids, mounts below
  the chroot) and only then uses sudo for `teardown` (common.sh: chroot processes by
  /proc/PID/root, helpers, `arecord`/`ffmpeg`/tesla-touch by pattern, mounts deepest first,
  the image if the run mounted it).
- Service loops print `tesla: SVC exited (N), restarting in 2 s [t=EPOCH]`; the summary ignores
  exits within 2-3 s of the stop (for older logs without t=: an exit in the last two lines).
  Same for the audio pipeline loop (Ctrl+C reaches pw-play/arecord too).
- `pkill -f` patterns in teardown use `[x]` so they don't match their own `sudo pkill` parent.

## Checks (`./tesla check`)
Host tools (with apt package names), tesla-touch + udev rule, /dev/uinput, the image (mounted or
file; `debugfs -R "cat ..."` reads files from the unmounted image without root), kit version,
maps, per feature: CAN database or unicorn/pyelftools, snd-aloop (loaded as model3 / loaded
without the id / available), sox/arecord/pw-play, music folder (audio file count), camera
devices + ffmpeg, GPS receiver readable, `--to` needs maps; ports of the services (TCP 4220 4160
4030 4190 4060 8002, UDP 1234 1235 4321 20100 63277, VNC, panel) via `ss`, podman containers.

## Kit version stamp
`mcu3_patch.py` writes `/etc/mcu3-patchkit` (kit = sha1 of mcu3_patch.py + src/*, commit, date,
skipped) after an error-free run when something changed or the stamp differs. `--kit-version`,
`-q` (only non-ok lines, section headers lazily), `--check` describes text file differences
(missing / N lines new or changed / removed). Any edit (also comments) makes a new version.
The user's image was stamped this session (f5ebc49621b9); `mcu3_patch.py` changed after that
(check message), so `./tesla check` will ask for one more `./tesla build-image`.

## ./tesla build-image
Update (mount if needed, kit `-q`, maps if newer tiles for the installed region exist or
`--maps REGION`), `--check`, `--fresh` (new image from mcu3-original/ into IMAGE.new, the old one
becomes IMAGE.old; asks first), `--sandbox` (sandbox/rootfs, no sudo), `-- KIT OPTIONS`.
`--fresh` is untested (it needs sudo and 6 GB).

## Log summary (`tools/logsummary.py`, `./tesla logs`)
Features, QtCar (exits from events.log: restarts for settings vs unexpected), service restarts
with exit codes and times, `journalctl -k` segfaults/traps/OOM in the run's time window,
audio (audiod pump errors, sox clipping, underruns, pipeline restarts), GPS (tesla-gps status
lines: RMC status, sats, GpsManager fix ratio), camera (ffmpeg messages), known error patterns
per log. `--list`; RUN can be a name prefix. `service_status()` is shared with `./tesla status`
and the panel. Checked against old runs: e.g. 20260923-232051 shows the DataValueWriter
segfault in libQtSql, 20260923-204102 the "port 4160 busy".

## Panel
- `tesla-can.py --http-bind` (default 127.0.0.1 now; `--remote` passes 0.0.0.0) and
  `--log-dir`: a "Services" section (up/down per service and helper, restart counts, links to
  every log and the summary; `/logs/NAME`, last 400 lines, `?all=1`; `/logs/summary`).
- Who set a value: control messages may carry `"source"`; tesla-gps.py `--can` sends
  `"source": "gps"`. `snd.owner` is cleared when the panel sets the value. The panel shows a note
  in "Drive" and GPS badges on drive rail, gear, speed and on the live shiftState/vehicleSpeed/
  odometer/driveRailOn.
- Not done: starting/stopping audio, camera, music from the panel (needs root: mounts, modprobe,
  chroot services). The sudo keepalive would make it possible, through a control FIFO read by
  the start script.

## Rootful container instead of the chroot (decided: not now)
Would give its own mount namespace (no leaked mounts) and `podman stop` as the kill switch. The
work: touch via `--device` after tesla-touch has created its event node (like sandbox.sh),
the net_cls cgroup mount for escalator/CEF inside a privileged container, /dev/shm via
`--shm-size`, `sudo podman exec` instead of `sudo chroot` for services/QtCar, and
`stop_chroot_procs` (readlink /proc/PID/root doesn't work across mount namespaces) replaced by
podman. Everything (browser, audio, camera, videos) would need a sudo re-test. With the new
stop/teardown the gain is small; the user chose to keep the chroot.

## USB "Loading..." = audio services waiting 50 s for the gateway (fixed)
- The USB browse source waits for "system ready" (`WaitingOnSystemForFirstWakeState`), which
  comes with `AUDIO_audioSource` from QtCarAudiod. In every real audio run qtcar-audiod and
  audiod printed nothing for ~50 s (logs/20260924-173236: their logs empty, `./tesla status`
  DOWN). `./tesla start --strace qtcar-audiod` (new) showed it: `qtcar-service` calls
  `/usr/bin/audio-type`, which runs `gw-diag GET_CONFIG_DATA 0 31`: UDP to the gateway
  `gw` = 192.168.90.102:3500, 10 s receive timeout, 5 tries, then it uses `[audiod] audio_type`
  from settings.conf (the kit sets `base`) anyway. The packets went out to the LAN.
- In the sandbox it returned at once (probably an ICMP error in rootless podman's network), so it
  never showed there.
- Fix: `qtcar-service` has its own `audio_type()` that reads the setting and only falls back to
  `audio-type`. Not verified in the real chroot yet (needs `./tesla build-image`, then a start with
  `--audio --music`: USB should list at once; `./tesla logs` flags services without output now).
- Other gw-diag users in the firmware: `touch-updater.sh`, `selftests/btwifi-selftest.sh` (not run).

## Are all the QtCar patches needed? (started, 2026-09-24 evening)
- **Dev vs prod mode**: `Logger::logAssert` crashes on purpose when `RuntimeEnv` mode != 2 (the
  reason for `utils-assert-nonfatal`). The mode defaults to 2 ("prod") in `RuntimeEnv::RuntimeEnv`;
  `RuntimeEnv::setFromArgs` sets it to 0 ("dev") when no address options are given (0xd72c6, our
  loopback setup) or with `--dev`, and back to 2 with **`--prod`** (0xd7151, compares "prod").
  Found with a gdb hardware watchpoint in the sandbox (`sandbox.sh -x`, new `QTCAR_ARGS`).
- `QTCAR_ARGS=--prod ./sandbox.sh`: mode 2, still loopback (LH 127.0.0.1, LHB 127.255.255.255),
  asserts only logged. Side effect: prod changes feature defaults, QtCar restarts once
  ("DVs changed: FEATURE_laneDepartureWarningEnabled, FEATURE_vectorMapTilesEnabled") and the map
  stays empty (vector tiles need Tesla's servers). Deleted those two flags from the sandbox DB
  again. To use `--prod` instead of the assert patches, pin `FEATURE_vectorMapTilesEnabled=false`
  (not tried yet).
- Patch triage (not acted on): dead/no-op on a fresh image: `gui-escalator-*`,
  `gui-cgroup-exit-*` (QtCar uses its own copy), all `*-revert` entries, the `chrome-sandbox`
  patches (CEF runs with no_sandbox and doesn't use it). Probably replaceable by `--prod`: the
  `utils-assert-*`, `media-assert-pause`, maybe `gui-energy-*`. Only testable in the real chroot:
  `qtcar-cgroup-exit-*` (escalator cgroup setup). Needed: `audiod-no-a2b`, `sim-no-di-*`,
  `cef-no-oscillator` (a bug in Tesla's CEF build).

## Native screen on a touch laptop (2026-09-24/25)
- Test machine: ThinkPad T480 (i5-8350U, 23 GB RAM, UHD 620, 1920x1080 ELAN touchscreen), Debian
  13 live (Xfce) booted from USB, user `user` with passwordless sudo, reachable over ssh. The
  image (4.1 GB used) went over as `zstd | ssh | dd conv=sparse` into the live system's RAM in
  20 s; repo via rsync of `git ls-files`. Nothing on the laptop's disk was touched.
- QtCar on the real X server (:0) worked at once: `DISPLAY=:0`, the session's cookie copied into
  the chroot (`xauth nlist | sed 's/^..../ffff/'` = FamilyWild), the touchscreen's event node
  bound as `/dev/input/touch` (+ ACL for uid 1111): touch worked directly.
- 1920x1080 panel: QtCar's `--size 1920x1080` lays out for 1080 (status bar visible) but clips
  the car panel's bottom; the user wanted black bars. Now: `xrandr --fb 1920x1200 --transform
  s,0,-offx*s,0,s,-offy*s` (s = 1.1111, offset 96 panel px): xrandr prints "screen not large
  enough" but applies it; the WM makes QtCar fullscreen, it draws 1920x1200. QtCar's
  EvDevTouchDriver has rotate/invert/range/rangex/rangey/autorange but no offset, so
  `tesla-touch --from DEV --panel WxH` (new, src/passthrough.rs) grabs the real touchscreen
  (EVIOCGRAB: the desktop doesn't see it), maps MT slots through the letterbox and re-emits them
  on its virtual device (range = UI size, QtCar autoranges to 1920x1200).
- `./tesla start --native` (SCREEN=native): no Xvfb/x11vnc/viewer; checks xrandr/xauth/the
  display/the touchscreen (`find_touchscreen`: ABS_MT_POSITION_X + INPUT_PROP_DIRECT); state has
  NATIVE and NATIVE_RESTORE (xrandr) for the teardown; xset s off -dpms while running. The kit's
  startup.sh takes QTCAR_DISPLAY/QTCAR_XAUTHORITY/QTCAR_ARGS; qtcar-service passes XAUTHORITY to
  tvideo. `sudo_auth`: `sudo -v` asks for a password on the live system despite NOPASSWD (it
  checks all rules), `sudo -n true` first.
- The kit built its shims with the laptop's gcc (glibc 2.41): all fine (<= 2.17), and the kit now
  refuses a built shim that needs a glibc newer than 2.22 (`check_glibc`, objdump -T).
- Ran `./tesla start --native --vehicle` on the laptop: services up, car data shown. Not yet
  checked: the letterbox on the panel and touch accuracy (the user looks), `./tesla stop`
  restoring the screen, audio (the laptop's own card), a bootable live stick.
