# Session 3 (2026-09-22 / 23): reconstruction, tooling, services, navigation

## Starting point
A working chroot image from May (`MCU2/mcu3.ext4`) without notes on how it was made. The first
session had been incognito.

## Reconstructed
- Compared `mcu3-original` with the image file by file, using `debugfs` on the image without
  mounting it.
- The chroot's `/root/.ash_history` held most of the May work.
- Everything went into `mcu3-patchkit/mcu3_patch.py`:
  - 20 byte patches, each checked against the original bytes and the files' SHA-1
  - Mesa 18.0.5 / LLVM 6.0 libraries
  - config, symlinks and `startup.sh`
- The patched binaries come out byte-identical to the May image.
- `icu_preload.c` was recovered; `fake_sandbox.c` was rebuilt from its binary.
- `sources.toml` lists verified download URLs (Ubuntu 16.04 packages) for all 17 libraries, so
  the kit works without `payload/`.

## Touch input: tesla-touch (Rust), replaces make_touch.py and click_bridge.py
- Reads mouse input from Xvfb as it happens (XRecord) and turns it into a uinput multitouch device
  (`cyttsp6_mt`). Controls: drag = finger, wheel = pinch zoom, right click = long press.
- Puts a normal arrow cursor on QtCar's windows (XFixes), so any VNC client shows a lag-free cursor.
- Bind-mounts only its own event node into the chroot.
- Problems found and fixed:
  - The host desktop adopted the virtual touchscreen as a real one. `99-tesla-touch.rules` hides it
    and sets `MODE=0666`.
  - QtCar's `EvDevTouchDriver` only reports a touch once it has both X and Y, and the kernel drops
    values that repeat. Repeated taps on the same pixel and pinches were lost. A touch that would
    repeat a coordinate is now shifted by 1 px.
- The viewer can be anything that speaks VNC: KRDC, remote-viewer, macOS Screen Sharing over an
  SSH tunnel, … VNC listens on localhost only by default.

## start_all.sh
- Paths are relative to the repo, so it works from any clone location.
- Logs go to `logs/<time>/` (QtCar, services, Xvfb, VNC, touch).
- Ctrl+C: sudo takes over the terminal, so the script checks QtCar's exit code (130/137) to tell a
  Ctrl+C from QtCar's own restarts ("CID UI is restarting").
- `SERVICES="..."` starts extra firmware services before QtCar. Navigation starts automatically
  once maps are installed.

## Firmware services
- `qtcar-service <job>` (from `mcu3-patchkit/src`) starts any of the 17 `qtcar-*` runit services
  like the car does, minus minijail, AppArmor and cgroups. All 17 run.
- Services must run **without** `--gw`/`--ip`. With those they publish to multicast 224.0.0.26,
  and QtCar listens on 127.255.255.255.
- `qtcar-vehicle` is the CAN↔data-value bridge. It expects CAN frames as UDP on :1234 / :31415,
  which is where fake vehicle data would go in.
- `QtCarSimService` is Tesla's vehicle simulator (486 `SIM_*` signals) and isn't used yet.

## Navigation: works offline, Northern California
- The chain is QtCar → `QtCarTMServer` → Tesla's modified `valhalla_server` 2.4.3 (localhost:8002)
  → tiles.
- Tiles are built from an OSM extract with upstream Valhalla 2.4.3 in podman (`navigation/`), and
  Tesla's fork reads them.
- What QtCar needs (all done by `install-maps.sh`):
  - tiles in `/opt/navigon/tm/NA/valhalla` (the US region folder is **NA**) plus `/opt/navigon/VERSION`
  - `[nav] forcePremiumNav=true`, otherwise QtCar waits for a map region from CAN
  - **no** `forceMapRegion=US`: "US" becomes region "none", navigation turns off, and that state is
    saved in `QtCarSettings.db`. US is the default (0); `EU`, `CN`, `AU` work.
- Valhalla has to start with a clean environment. The host's `LANG`/`LC_*` come through sudo, those
  locales don't exist in the firmware, and every route fails in the turn-instruction step.
- Online routing: Tesla's Navigation Service (`maps-prd.go.tesla.services`, modes disabled /
  primary / shadow, set through `FEATURE_navigationService*`). It needs the car's client
  certificate. Idea: point it at your own Valhalla server.

## Other findings
- QtCar as `tesla` reads `/home/tesla/.Tesla/car/settings.conf`, and as root it reads `/root/...`.
  Until this session only `/root` had the Model 3 config.
- The fake `chrome-sandbox` in the payload needs glibc ≥ 2.34, and the chroot has 2.22. Built from
  `src/` it's static. The browser still doesn't work, and the `gui-cef-nosandbox` patch breaks the
  argument setup of the `cef_initialize` call.
- QtCar restarts itself when feature flags change (e.g. on first boot). `start_all.sh` restarts it.

## Browser (end of session, not finished)
- CEF starts in the real chroot ("CefInitialize success", zygote and renderer processes come up).
  It stays invisible because QtCar gets its pixmap through `eglCreateImageKHR(EGL_NATIVE_PIXMAP_KHR)`,
  which Mesa swrast on Xvfb can't do ("eglCreateImageKHR error 0x3000").
- `mcu3-patchkit/src/egl_pixmap_shim.c`, preloaded in `startup.sh`, emulates that: it copies the
  pixmap into the texture on each bind. **Not tested yet with a live browser.** Debug output goes to
  qtcar.log (`egl_pixmap_shim: ...`, via `EGL_PIXMAP_SHIM_DEBUG=1`).
- The `gui-cef-nosandbox` patch writes to `0x10(%r11)`, a random address, and leaves the
  `cef_initialize` arguments unset. That's a likely cause of crashes ("tcmalloc Memory corruption
  detected"). A clean replacement: drop the patch and set `no_sandbox` with an LD_PRELOAD hook on
  `cef_initialize` (see `cef_nosandbox.c` from May; pin dlsym to `GLIBC_2.2.5`).
- **Test 2026-09-23 12:00 (logs/20260923-115859):** the shim works ("stand-in image for pixmap
  0x1200051", texture created), but the pixmap is 0x0: CEF's **render process crashes** right after
  starting ("render process crashed 1 times, reload", 4x), so nothing is drawn. There's no CEF log
  file and no minidump. Most likely cause: the renderer sandbox (namespaces/seccomp) in the chroot.
  Next step: remove `gui-cef-nosandbox` (`--skip` alone doesn't undo it on an already patched
  image; restore the original bytes), set `no_sandbox` via a `cef_initialize` hook, and get CEF
  logging (e.g. `--enable-logging --v=1` via the hook or command-line switches).
- **Cause of the renderer crashes** (from the kernel log, `journalctl -k`, readable as a member of
  group adm): `tesla-cef-zygot: segfault at 0 ... error 6 in libcef.so[4165885,...]`, the same
  place every time. At that address in `/usr/lib/libcef.so` is an **AVX** loop
  (`vmulps`/`vmovaps %ymm1,(%rdx,%rcx,1)`, float array × scalar, probably Chromium's vector math)
  that writes to a null target pointer. The car's Atom CPU has no AVX and takes the SSE path; this
  PC does have AVX. It isn't the chroot or the sandbox (there's no AppArmor denial). Next step:
  identify the function and its CPU dispatch (base::CPU / cpuid) and force the SSE path by byte
  patch; if instead an allocation just before it fails, look at the memory settings.
- Running Chromium outside the chroot isn't a shortcut: QtCar loads libcef in-process and drives it
  through the CEF C API, so it would take a full libcef replacement.
- Hardware rendering isn't realistic: the host has an NVIDIA RTX 4060 with the proprietary driver,
  and the chroot's Mesa 18 knows neither.
- In the sandbox CEF dies before displaying anything, because `/usr/bin/escalator` wasn't readable
  when the sandbox was copied (root-only). Fix: `sudo cp mcu3-original/usr/bin/escalator
  sandbox/rootfs/usr/bin/ && sudo chown $USER sandbox/rootfs/usr/bin/escalator`.
